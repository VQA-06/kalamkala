# @kalamkala/db-schema

Drizzle ORM schema for the Undangan Digital Cloudflare D1 database. This package
contains table definitions only. Migrations are generated into `./drizzle` and
applied with Wrangler.

## Conventions

- **IDs**: `text` primary keys generated by the application (UUIDs). No database
  default is declared.
- **Money**: `integer` rupiah amounts. There are no cents and no floats.
- **Time**: `integer` Unix seconds using `{ mode: 'timestamp' }`. `created_at`
  and `updated_at` default to `sql\`(unixepoch())\``; `updated_at` also uses
  `.$onUpdate(() => new Date())`. That refresh happens in the ORM, not in a
  database trigger, so raw SQL writers must set the column themselves.
- **JSON**: `*_json` columns are plain `text` with SQL string defaults (`'{}'` or
  `'[]'`). They are parsed and validated at API boundaries, never by Drizzle's
  `{ mode: 'json' }`.
- **Appearance**: `invitations.appearance_json` is nullable and has no default.
  `null` means the host has not overridden the template palette, so renderers
  fall back to the template's first palette.
- **Reports**: `invitation_reports` stores abuse reports for admin triage. Only a
  `reporter_hash` is persisted; raw IP addresses are never stored.
- **Booleans**: `integer` columns with `{ mode: 'boolean' }` and an explicit
  default.
- **Enums**: every enum column is `text(col, { enum: CONST })` and also has a
  real CHECK constraint. The SQL value list is derived from the tuple exported by
  `@kalamkala/contracts`, so there is a single source of truth. Direct SQL
  writers cannot insert values the application does not know.
- **Foreign keys**: invitation-owned children cascade; `rsvps.guest_id` uses
  `set null` so messages survive guest deletion; `invitations.template_id`
  references `catalog_templates.id` without a cascade, so templates in use
  cannot be removed; `sessions`, `accounts`, `invitations`, and `transactions`
  cascade from `users`.
- **Indexes**: declared explicitly in each table's extras callback and named
  `<table>_<column>_idx` (or `_unique` for composite unique indexes).
- **Aggregate schema**: `schema` exports all tables as one const object, used to
  type a client as `DrizzleD1Database<typeof schema>`.

## Generating migrations

From this package:

```sh
pnpm drizzle-kit generate
```

This writes SQL migrations to `./drizzle`. It does not need D1 credentials or a
local database. Apply them with:

```sh
pnpm wrangler d1 migrations apply <DATABASE_NAME> --remote
```

## Better Auth compatibility

Our table names are plural, while Better Auth's Drizzle adapter resolves models
by its internal singular keys (`user`, `session`, `account`, `verification`).
Pass an explicit mapping when creating the adapter:

```ts
import { drizzleAdapter } from 'better-auth/adapters/drizzle'
import {
  accounts,
  sessions,
  users,
  verifications,
} from '@kalamkala/db-schema'

const auth = betterAuth({
  database: drizzleAdapter(db, {
    provider: 'sqlite',
    schema: {
      user: users,
      session: sessions,
      account: accounts,
      verification: verifications,
    },
  }),
  // ...providers, secret, etc.
})
```

The mapped columns follow Better Auth's SQLite model: `email_verified` is an
integer boolean, timestamps are integer Unix seconds, `sessions.token` and
`users.email` are unique, and `accounts` is unique on `(provider_id,
account_id)`. Better Auth field names (`emailVerified`, `accessTokenExpiresAt`,
and so on) match the Drizzle property names above.
